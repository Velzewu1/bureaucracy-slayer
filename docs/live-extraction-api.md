# Live Sonnet extraction API contract

Status: contract for the P0 controlled demo. Backend and frontend implementation are intentionally out of scope for this change.

Runtime schemas live in `src/orchestration/live-extraction-contract.ts`. They are additive transport contracts and do not change the schema or meaning of `SiteSnapshot`, `ProcedureModel`, `EvidenceResult`, `UserState`, or `SafeActionPlan`.

## Decision

Use one asynchronous job resource with HTTP polling:

- `POST /api/live-extraction/jobs` starts or resumes an idempotent request.
- `GET /api/live-extraction/jobs/:jobId` returns progress or a terminal result.

The roughly one-minute pipeline has two Claude stages, so a synchronous request is too fragile for browser and development-proxy timeouts. Polling is simpler than WebSockets or server-sent events, supports deterministic cleanup, and requires no streaming infrastructure. There is no cancellation endpoint in P0: cancelling in the UI stops polling but cannot honestly promise to abort the current Playwright or Anthropic operation.

The server owns the only permitted target and goal:

```text
Portal: http://127.0.0.1:5180/dashboard
Goal:   I sent an $850 transfer to the wrong recipient. Can I cancel it? If not, what are my alternatives?
```

Neither value is accepted from the browser.

The shared schema does not hardcode the mock-portal route in production code. The server loads the portal from its trusted startup configuration, which is fixed to the value above for this MVP, and emits the actual goal and portal in the result. Cross-object refinements require that the snapshot root, extraction goal, and source-selection bindings agree. Integration tests assert the exact P0 configuration.

## Trust boundary and data flow

```text
Browser                Loopback API                    Existing deterministic/probabilistic pipeline
POST fixed command --> one bounded job --> collectWebsite(fixed portal)
                                            select goal-scoped sources
                                            Sonnet Stage 1: policy extraction
                                            Sonnet Stage 2: procedure mapping
                                            canonical conversion
                                            semantic qualifier audit
                                            evidence validation
GET/poll <---------- canonical snapshot + model + evidence + audit
strict parse
recompute hashes
rerun the same audit and evidence validator
evaluate and plan locally for user facts
```

The backend must run conversion, semantic audit, and evidence validation before publishing a result. The browser then uses the same shared hashing, audit, and evidence-validation implementations to verify the returned artifacts. This is defense in depth with one implementation of each semantic rule, not two divergent validators. The browser must use its locally recomputed `EvidenceResult` for evaluation and planning.

Exact evidence binding proves provenance, not semantic correctness. `semanticCoverage: "not_verified"`, audit findings, `EvidenceResult.status`, rule IDs, and evidence issues remain separate concepts. There is no `verified: true` field.

## Endpoint 1: start a job

### Request

`POST /api/live-extraction/jobs`

Required headers:

```http
Content-Type: application/json
```

Strict body, maximum 1,024 bytes:

```json
{
  "schemaVersion": 1,
  "action": "start_live_extraction",
  "requestId": "request_1234567890abcdef1234567890abcdef"
}
```

`requestId` is generated by the browser from 128 random bits and encoded as `request_` plus 32 lowercase hexadecimal characters. Unknown keys, a URL, goal text, model settings, user facts, or any other `action` are rejected. `UserState` is not part of extraction and remains local to deterministic evaluation.

### Accepted response

HTTP `202 Accepted` with `Location` set to `statusUrl`, `Retry-After: 1`, and:

```json
{
  "schemaVersion": 1,
  "jobId": "job_1234567890abcdef1234567890abcdef",
  "state": "queued",
  "statusUrl": "/api/live-extraction/jobs/job_1234567890abcdef1234567890abcdef",
  "pollAfterMs": 1000
}
```

The server creates `jobId` from independent 128-bit randomness. It is never sequential and is not derived from the API key, goal, portal, snapshot, or request ID.

### Idempotency and the single-active-job rule

- The first valid `requestId` creates at most one physical extraction job.
- Repeating the same `requestId` while its job or tombstone is retained returns the same `jobId` and does not call the collector or Claude again. The response remains `202`; the client follows `statusUrl` for current state.
- A different `requestId` while the single physical worker is occupied receives HTTP `409` with `JOB_ALREADY_RUNNING`.
- A timed-out logical job still owns the physical worker until its underlying work settles. A replacement job must not overlap it.
- Once the request-ID tombstone expires, a reused ID is treated as a new request. The UI generates a new ID only after an explicit new-analysis action.

## Endpoint 2: retrieve job status

`GET /api/live-extraction/jobs/:jobId`

Valid job IDs match `job_[a-f0-9]{32}`. A retained job returns HTTP `200` and exactly one state from the shared discriminated union.

### Queued

```json
{
  "schemaVersion": 1,
  "jobId": "job_1234567890abcdef1234567890abcdef",
  "requestId": "request_1234567890abcdef1234567890abcdef",
  "state": "queued",
  "phase": "queued",
  "createdAt": "2026-10-17T12:00:00.000Z",
  "updatedAt": "2026-10-17T12:00:00.000Z"
}
```

### Running

`phase` is one of:

- `collecting`
- `selecting_sources`
- `extracting_policy` (Sonnet Stage 1)
- `mapping_procedure` (Sonnet Stage 2)
- `validating` (canonical conversion, semantic audit, and evidence validation)

The running shape adds `startedAt`. Progress is phase-based; the server must not invent percentages.

### Succeeded

The terminal success adds `completedAt`, `expiresAt`, and `result`. The result contains only:

- the fixed goal and portal identity;
- the canonical `SiteSnapshot`;
- the canonical `ProcedureModel`;
- the backend `EvidenceResult`;
- a bounded goal-scoped source-selection summary, without selected source text;
- deterministic semantic-audit findings; and
- minimal provenance: `extractionType: "live"`, configured model name, and completion time.

The runtime schema enforces snapshot/model/evidence/source-selection identity and hash bindings, validates selected page IDs, and ensures semantic-review rule IDs exactly match audit findings. `EvidenceResult.status: "degraded" | "invalid"` and semantic audit findings are still a successful HTTP/job result because they are valid review-required outcomes. They must never be converted to a generic Claude or server failure.

The response excludes evaluation and planning. After local verification, the UI evaluates each new `UserState` with the existing pure evaluator and planner; replanning never calls this API.

### Failed

The terminal failure adds `completedAt`, `expiresAt`, and:

```json
{
  "error": {
    "code": "STAGE_2_RESPONSE_INVALID",
    "stage": "procedure_mapping",
    "message": "Procedure mapping returned an invalid structured response.",
    "retryable": false,
    "issueCodes": []
  }
}
```

Messages are sanitized, bounded, and safe for display. `issueCodes` contains only bounded machine-readable codes, never raw provider or Zod text. Neither field may contain SDK request IDs, response bodies, prompt text, page contents, credentials, headers, or stack traces. Callers branch on `code`, never message text.

### Missing or expired jobs

- Syntactically invalid ID: HTTP `400`, `REQUEST_INVALID`.
- Unknown valid ID: HTTP `404`, `JOB_NOT_FOUND`.
- Known tombstone after the large result was evicted: HTTP `410`, `JOB_EXPIRED`.

All error responses use `LiveExtractionErrorResponseSchema`. All job status responses, including terminal operational failures, use HTTP `200`; transport/resource errors use the status codes below.

## HTTP behavior

| Condition | HTTP | Code or body |
|---|---:|---|
| New or idempotently repeated start | 202 | `LiveExtractionStartResponse` |
| Retained job status | 200 | `LiveExtractionJobStatus` |
| Malformed JSON, invalid ID, or invalid strict schema | 400 | `REQUEST_INVALID` |
| Recognized request with unsupported `action` | 400 | `UNSUPPORTED_ACTION` |
| Wrong content type | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| Body over 1,024 bytes | 413 | `REQUEST_TOO_LARGE` |
| Different request while worker is occupied | 409 | `JOB_ALREADY_RUNNING` |
| Unknown valid job ID | 404 | `JOB_NOT_FOUND` |
| Evicted job with retained tombstone | 410 | `JOB_EXPIRED` |
| Unsupported HTTP method | 405 | `Allow` header plus `UNSUPPORTED_ACTION` |

Every response sets `Content-Type: application/json`, `Cache-Control: no-store`, and `X-Content-Type-Options: nosniff`. Unexpected handler exceptions are caught at the HTTP boundary and returned as sanitized `INTERNAL_ERROR`; the process logs no sensitive inputs.

## Operational failure taxonomy

| Public code | Stage | Existing source outcome |
|---|---|---|
| `CONFIGURATION_INVALID` | `internal` | Missing/invalid server model or key configuration; extractor `CONFIGURATION_INVALID` |
| `COLLECTOR_UNAVAILABLE` | `collector` | `BROWSER_LAUNCH_FAILED` |
| `PORTAL_UNAVAILABLE` | `collector` | `NAVIGATION_FAILED`, `NAVIGATION_TIMEOUT`, `PAGE_UNAVAILABLE` |
| `COLLECTION_SECURITY_BLOCKED` | `collector` | `ORIGIN_DISALLOWED`, `REDIRECT_DISALLOWED`, or `UNSAFE_REQUEST_BLOCKED` |
| `SNAPSHOT_INVALID` | `collector` | `SNAPSHOT_SCHEMA_INVALID` |
| `COLLECTION_FAILED` | `collector` | Other unexpected collection failure, sanitized |
| `SOURCE_SELECTION_INCOMPLETE` | `source_selection` | Extractor `SOURCE_COVERAGE_INCOMPLETE` |
| `STAGE_1_TRANSPORT_FAILED` | `policy_extraction` | `CLAUDE_REQUEST_FAILED` with `modelStage: policy_extraction` |
| `STAGE_1_RESPONSE_INVALID` | `policy_extraction` | `CLAUDE_RESPONSE_INVALID` with Stage 1 |
| `STAGE_1_OUTPUT_INVALID` | `policy_extraction` | `POLICY_EXTRACTION_INVALID` |
| `STAGE_2_TRANSPORT_FAILED` | `procedure_mapping` | `CLAUDE_REQUEST_FAILED` with `modelStage: procedure_mapping` |
| `STAGE_2_RESPONSE_INVALID` | `procedure_mapping` | `CLAUDE_RESPONSE_INVALID` with Stage 2 |
| `STAGE_2_OUTPUT_INVALID` | `procedure_mapping` | `PROCEDURE_MAPPING_INVALID` |
| `PROCEDURE_SCHEMA_INVALID` | `procedure_schema` | `PROCEDURE_SCHEMA_INVALID` |
| `EVIDENCE_VALIDATION_FAILED` | `evidence` | Structural `EVIDENCE_VALIDATION_FAILED`; ordinary degraded/invalid evidence remains success |
| `JOB_TIMED_OUT` | `timeout` | Wall-clock deadline exceeded |
| `INTERNAL_ERROR` | `internal` | Unclassified programmer/infrastructure failure, sanitized |

`retryable` is conservative UI guidance, not automatic retry authority. P0 never automatically creates another paid job. A user may explicitly start a new analysis with a new request ID after inspecting the failure.

## Lifecycle, limits, and timeouts

- Capacity: one physical worker, one active job, and at most two terminal jobs containing artifacts.
- Terminal retention: 15 minutes from completion, subject to the two-result cap; oldest terminal data is evicted first.
- Tombstones: retain only `jobId`, `requestId`, and expiration metadata for a further 15 minutes, maximum 16 tombstones, so the API can distinguish `410` from `404` without retaining site artifacts.
- Overall job deadline: 180 seconds.
- Collector: fixed start URL; allowed origin is exactly `http://127.0.0.1:5180`; at most 12 pages, depth 3, 10-second navigation timeout, at most one navigation retry, 30,000 visible-text characters, 200 blocks, and 100 actions per page.
- Extraction: fixed goal scope (`cancel the transfer`, alternative `request recovery`), two stages, no extractor-level transient retry in live mode, and no SDK-level automatic retry.

The current transport interface does not accept an `AbortSignal` and its SDK wrapper currently inherits a long default timeout and automatic retries. Before the live server is considered complete, the backend owner must add bounded transport configuration so each call respects the 180-second overall deadline and SDK retries are disabled. Until underlying cancellation is available, crossing the deadline marks the logical job `failed/JOB_TIMED_OUT`, discards any late result, and keeps the worker occupied until the underlying operation settles. The API must never claim the paid call was cancelled.

## Browser polling and cleanup

The Live provider owns exactly one `AbortController` and one timer per analysis:

1. Generate one `requestId` and POST once.
2. Parse every response with the shared runtime schema.
3. Poll `statusUrl` after `pollAfterMs` (1 second), with at most one GET in flight.
4. Stop on `succeeded`, `failed`, component unmount, mode switch, explicit UI cancel, or navigation.
5. Record the local stop as `user_cancelled`, `navigation`, `mode_changed`, or `component_unmounted` using `LiveExtractionClientStopReasonSchema`. This is UI state, not an HTTP response or server job transition.
6. Aborting or navigating away stops client requests only. It does not create a server cancellation claim and does not start a replacement extraction.
7. Retain `jobId` in the Live mode workspace while that workspace exists, allowing polling to resume without a second POST.

On success the provider must:

1. Strict-parse the complete artifact.
2. Recompute every evidence-block hash, website-action fingerprint, page hash, and site hash with `src/shared/hashing.ts`; reject any mismatch as stale/tampered.
3. Re-run `auditSemanticQualifiers(snapshot, model)` and compare the canonical result with `semanticAudit`.
4. Re-run `validateEvidence` using the returned evidence ID/time and recomputed audit findings; compare status, valid/rejected rule IDs, verified/executable action IDs, and structured issues with the server result.
5. Store the locally validated immutable snapshot/model/evidence in a Live-only session.
6. Run evaluator, planner, Decision Intelligence, counterfactuals, and adaptive questions locally. User-fact changes perform no HTTP, collection, or Claude call.

Any mismatch fails closed as an artifact-integrity error. The UI must not partially accept a server result.

## Network and security guarantees

- The API listens only on `127.0.0.1`, on the implementation-plan port.
- Vite proxies `/api` to the loopback API so browser requests are same-origin. The API does not send wildcard CORS headers; direct cross-origin browser requests are rejected by exact `Origin` checking.
- The server supplies the portal URL, goal, goal scope, collector options, model, and key. The request cannot influence them.
- Collector navigation remains limited to the configured start origin and allowlisted same-origin discoveries. Redirects to another origin, unsafe navigation methods, downloads, credentials in URLs, and unsupported actions fail closed.
- The collector's current guarantee covers top-level navigation and discovered links; it does not yet prove that every passive subresource request is same-origin. The implementation must not overstate the SSRF guarantee, and the integration-security owner should add a regression test before claiming subresource isolation.
- The Anthropic key remains server-side. Browser responses never include keys, workspace IDs, authorization/cookie headers, prompts, raw Claude envelopes, thinking/redacted-thinking blocks, SDK metadata, debug events, Stage 1/2 DTOs, or stack traces.
- The API exposes no browser-action or form-submission endpoint. Every plan step remains guidance-only and `autoExecutable` remains `false`.
- Responses and logs must not contain user fact values, credentials, cookies, tokens, full account numbers, or unredacted unrelated page content.

## Explicit non-goals

- Arbitrary portals or goal text.
- Server-side policy evaluation or planning for user facts.
- WebSockets, SSE, databases, queues, accounts, or multi-user scheduling.
- Guaranteed cancellation of already-started Playwright or Anthropic work.
- Automated navigation, form submission, transaction cancellation, dispute initiation, or any irreversible action.
